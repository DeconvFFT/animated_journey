## Answers to the five questions in the brief

**Does the maker get the Windows kit first, and can a learner run it safely?** First, yes: WP-02 hours today, WP-01 Tuesday, the Craft-zip guide Thursday, Ken Burns and archive Friday. Safely, mostly: the inventory is read-only, needs no admin, prints each step, refuses to write a report that fails its own redaction scan, and the README gives the two one-session execution-policy options a learner can paste without touching machine or user policy. Two things cut against safety. `lj.ps1 close` v0 (with `-Apply`, which deletes, and `-Commit`, which runs git) sits inside the same Tuesday package as the inventory, so the first thing a learner downloads contains the one tool that can remove files; and its target lists are admitted to be empty and UNVERIFIED until the Sat 24 Oct five-minute tests tell us where each app writes. Build it after that date, not before (nudge 1). Second, the self-scan "refuses to write" on any hit including 4-character fragments of the user name; a user name such as "asus" or "dell" will match a hardware string and block the maker on day one with no path forward unless the refusal names the category and the README says what to do (folded into nudge 1).

**Are the packages independent within each wave?** Yes on paper: every cross-package call either reads a frozen interface or is explicitly "skipped until X lands" (WP-04 A11, WP-09's `spec_check` lines, WP-07's `check_guide.py` using pwsh "if present"). Two couplings are not declared: disk is a shared resource with no mechanism (section 4.9 states a rule, "WP-07 is the only package allowed to hold more than 300 MB", but four parallel subagents have no way to honour it), and the redaction rules are re-implemented in WP-01, WP-03 and WP-09 with no shared source, so "consistent redaction" is a hope, not a dependency.

**Are the acceptance tests real?** Largely yes, and better than usual: `?random=1` proves the determinism test can fail; `?push=layout` proves MO8 can fail; the bare `-pix_fmt` oracle proves `spec_check.py` alone is not enough; the byte-flip tamper test, the corrupted tarball, `FORCE_BAD_ASSET`, the dead-allowlist audit, the planted-tree stale test and the "no false positives on six good files" line are all tests that fail when the thing is broken. Three are not: WP-08's `--selftest` asserts a *prediction* ("FontSize-23 FAILS portrait") as a pass condition, so an honest measurement that disagrees would fail a working tool (nudge 5); WP-02's card test is string presence (acceptable for a document, noted); WP-04 A7's "at least N ink pixels" leaves N unset (set it from the blocked-font baseline, fold into WP-04's own work).

**Over-engineered for a 9-12 minute film?** Three places. `lj.ps1 close -Commit` and `-IncludeWindowsRecent` in v0 (W-26 wants them by Sat 14 Nov, not Tue 20 Oct). SP1 T5 SoundCraft: the app is unpinned, learning-only and barred from the delivery path (D-12); its test "gates nothing" by the plan's own words, so it costs disk, time and a review for nothing this fortnight (nudge 7). WP-07 fetches PhotoCraft, VectorCraft and LightCraft for T1 only and WP-10 fetches all three again for read-backs: about 317 MB downloaded twice on a 1.3 GB disk (nudge 6). Everything else earns its place: the phone package is the D-27 proof, the validators are the G6 gate for every later shot, and the stale check is a register row (W-29).

**Missing for P-LOCK?** Within weeks 1-2, no must-pass item is unaddressed and the deferrals in section 9 (manifest schema, the three W-31 skills, `lj.ps1 close` v1, SP3, SP4, r10) are the ones ROADMAP itself puts in weeks 3-4. Two things the fortnight does need and the plan lacks: the fill-crop phone scenario that review 04 computed (a 16:9 picture filled to a 20:9 phone loses about 10% of picture height top and bottom, so a caption at the 5% margin is cut in half), without which the phone row on the Sun 1 Nov card is measured against the wrong failure (nudge 5); and the regional-script question (nudge 4), because O-10 arrives Sun 25 Oct, inside this plan's window, and W-57 puts font and caption tests on the Sun 1 Nov card.

**Is the public-repo redaction rule designed in, not bolted on?** Designed in at the data level (4.4's "deliberately not collected" list, 4.2's envelope rules, ID-only GATHER.md, README wording, local deny list). Bolted on at the code level: the identifying-data scan is written in PowerShell inside `step0_pc_tests.ps1`, again in Python inside `windows_check.py`, again inside `public_lint.py`, and a fourth time ("self-scanned like WP-01") inside `run_checks_pc.ps1`, by three owners, with no shared pattern file or shared positive/negative samples. One scanner will accept what another rejects (for example a 64-hex ffmpeg binary hash, which WP-09 wants to keep and WP-01's "serial-like strings" rule would flag). And the raw PC report, a hardware fingerprint of the maker's machine, is routed into the public repo via `build/evidence/pc/`. Nudge 3 fixes both.

## Nudges (8)

1. **Split WP-01; re-wave the destructive half.** WP-01a (Tue 20 Oct, reviewed by Fable before the maker runs it): `step0_pc_tests.ps1`, `windows_check.py`, `win/tools/*`, `pins.json`, the schema, fixtures, `README-MAKER.md`. WP-01b (wave 2, after Sat 24 Oct when the five-minute tests show where each Craft app writes): `lj.ps1 doctor` and `close` v0 as **dry-run-only** (list what it would remove; no `-Apply`, no `-Commit`, no `-IncludeWindowsRecent` until v1 in week 4, per A-04). In WP-01a, the self-scan refusal must print the category and the masked hit (first two characters plus asterisks), and the README's "what to do if it fails" section must cover a false positive on a short user name. Add a fixture `report_short_username_collision` (a 4-character user name that also appears in a GPU string) and decide the rule: a hit inside a field that is itself a hardware name is reported, not refused.

2. **Make disk a mechanism, not a rule.** Add a `disk.lock` beside `bench.lock`: any write over 100 MB takes it, runs `df`, and holds it until its cleanup. Replace the 2x guard with "Avail minus planned write must stay above 400 MB" so WP-07's 600 MB peak is possible on this container once pwsh (200 MB) is resident; with the 2x rule WP-07 exits 3 on day one (1.3 GB minus 200 MB is below 1.2 GB). Ask the orchestrator today whether the pip cache (418 MB, regenerable) may be cleared before wave 1; put the answer in the plan. Record `df` in every evidence envelope so WP-11 can show the budget was kept.

3. **One redaction source, read by every scanner, and the raw PC report never enters the repo.** Add section 4.13, a frozen interface `scripts/redaction_patterns.json` (owner WP-03, but delivered **today**, before WP-01a, since it is a small file): categories (email, IPv4 with documentation ranges allowed, IPv6, MAC, Windows and Linux profile paths with the three placeholders, token shapes, GUID/serial shapes with an explicit exemption for 64-hex SHA-256 values, handle shapes), each with `positive_samples[]` and `negative_samples[]` built from fragments. `step0_pc_tests.ps1` and `run_checks_pc.ps1` load it with `ConvertFrom-Json` (5.1-safe); `windows_check.py` and `public_lint.py` import it; `public_lint.py --self-test` runs every sample through all four consumers' regex sets and fails on any disagreement. Then: the raw `pc_report.json` and `colour_patch_pc.json` are read by the maker and pasted in chat only; what WP-11 files under `build/evidence/pc/` is the derived tier JSON (`gpu_tier`, `ram_tier`, `edition`, ffmpeg version and binary hash, chain results), never the hardware inventory. `ops/HOURS-HOWTO.md` adds one line: "no names in `note`, IDs and relation tokens only", and `ops_lint.py` checks `note` against the pattern file.

4. **Parameterise the script; do not assume Devanagari.** D-28 names "her regional language"; O-02 and O-10 (due Sun 25 Oct) will say which script, and W-57 puts the font and caption tests on the Sun 1 Nov card. Make `pipeline/phone/test_strings.json` keyed by script with Devanagari as the day-1 entry and the Noto family named per script in `libs.lock.json` (one extra `npm pack` once O-10 arrives); make WP-08's mark-survival check read per-script mark positions from the same file (Tamil, Telugu, Kannada, Malayalam, Bengali and Gujarati differ in where and how marks stack); and have WP-04's A7 and WP-08's IoU test run for every script listed, not one. The neutral words stay "checked by a person who reads the script" (the maker). The settings card's language note (WP-02 item 4) should say the caption test ran in script X on date Y.

5. **WP-08: add the fill-crop scenario and turn the prediction into a finding.** Add scenario `fill_20x9` (16:9 picture filled to a 20:9 portrait or landscape screen, about 10% of picture height cropped top and bottom) and a caption-position metric (bottom of the caption box as a percentage of picture height), with a `(J)` threshold that keeps the box above the crop line; `PHONE-ROW.md` then carries a caption **position** as well as a size. Rewrite `--selftest` so it asserts mechanisms only: a known-tiny caption fails portrait, a known-large one passes, the 1-px hairline fails `shared`, a caption at the 5% margin fails `fill_20x9`. The FontSize-23 verdict per scenario is written to the evidence JSON as a finding, whichever way it comes out.

6. **Re-wave the three visual-app fetches so each tarball is downloaded once.** WP-07 fetches and runs FilmCraft and EffectCraft only (T1, T2, T4); PhotoCraft, VectorCraft and LightCraft move wholly to WP-10, which runs T1 and the read-backs while the tree is on disk, one app at a time. WP-07 still fetches every `SHA256SUMS.txt` on Tuesday so `release_assets.json` and the maker's Craft-zip guide are complete for Sat 24 Oct. Saves about 317 MB of downloads and one round of disk churn.

7. **Cut SP1 T5 (SoundCraft) from this fortnight.** D-12 bars SoundCraft from the delivery path and leaves it unpinned; the plan says T5 "gates nothing". Record it as "not run: learning-only app, no decision depends on it" in `VERDICTS-W2.md`. Re-open only if the maker asks to learn the app.

8. **Review at wave boundaries, with one exception.** Eleven package reviews plus this one is more Fable time than the fortnight has and more hand-offs than the orchestrator should carry. Fable reviews WP-01a alone (before the maker runs it, Tuesday morning), then wave 1 as one bundle on Fri 23 Oct with `run_week2_checks.sh --quick` output attached (WP-11 should therefore deliver the runner's skeleton in wave 1, even if it only runs the packages that exist), wave 2 on Wed 28 Oct, and WP-11's readiness map on Fri 30 Oct. Definition-of-done item 5 stays; the cadence is what changes.

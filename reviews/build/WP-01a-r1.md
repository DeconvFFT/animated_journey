## 3. Tests of my own, designed to break it

1. **ffmpeg version strings with no leading number** (common Windows builds: BtbN `N-118000-g1a2b3c4d5e-20260101`, Gyan git `2026-01-01-git-abc1234-full_build-www.gyan.dev`, `n7.1.1-3-gabcdef`). Result: `windows_check.py` exits 0 with no INFO or FINDING, prints the raw string in the table, and writes `"version": null` into the tier file. The 6.x floor is never judged for such a build. A `5.1.2` build correctly produces the floor FINDING and exit 1. This is the one correctness gap I found; the SHA-256 still identifies the build and the colour-patch test runs on whatever build is present, so it is a nudge, not a blocker (nudge 1).
2. **Realistic Windows account names** as `--forbid` against six clean fixtures: `Dell`, `Lenovo`, `Asus`, `Acer`, `User`, `Admin`, `Home`, `Owner`, `Intel`, and four common Indian given and family names. None refuses; `Intel` and `Home` land in hardware-name fields as NOTE only. Only the words `Windows`, `found`, `path` and `tools` refuse, through the script's own note strings and the `WindowsPowerShell` edition label; none is a plausible account name. The hardware-name rule works as nudge 1 of the round-2 review intended.
3. **Linux dry run leak check**: the written report and the console contain no `/root`, `/home/` or `C:\Users` string; the only name-check line is the honest `NOTE name check skipped for a computer_name of 2 character(s)` (the container's host name is two characters; nothing about it is printed).
4. **Lint evasion**: `ps_lint.py` blanks strings and comments, so a quoted `Set-ExecutionPolicy ... LocalMachine` inside a string is not flagged; but any way of running that string (`Invoke-Expression`, `iex`) is caught by the `RO-eval` rule, and the real README passes with `-Scope Process` only. Acceptable for a safety net that the parser and the maker's run back up.

## 4. Findings by criterion

**Correctness (4).** Everything the plan lists passes and I reproduced the important ones. The two-pass self-scan (scan, record the NOTEs into the report, scan the final object again) is the right shape. The nvidia-smi then `qwMemorySize` then flagged `AdapterRAM` chain, the capped-field refusal to trust, the fallback by index when names differ, and the non-NVIDIA cap are all data-driven and tested with mocks. Gap: the ffmpeg version parsing above. Robustness point: step 9's `Get-ChildItem -Path $base -ErrorAction Stop` on the display-adapter class key will abort the whole registry read if one child key (the ACL-protected `Properties` key, in my memory of the provider's behaviour, UNVERIFIED) cannot be opened; `SilentlyContinue` there loses nothing (nudge 2).

**Safety and privacy (5).** Redaction is designed in at every layer the plan asks for: fail-closed load of the one pattern file (checked before anything is collected), masked hits with category and field, the hardware-name NOTE rule, names read from the environment and never stored, `%TEMP%` printed unexpanded, `Show-Path` on every echoed folder, `Clean-Message` on every exception text, the local deny list in any Notepad encoding, the derived tier file with `additionalProperties: false` and a leak test that greps every fixture model string out of it, `--forbid` kept out of the maker README (round-2 nudge 7), `shared_pc_hint` cut from the filed file (nudge 4), `py -0` instead of `py -0p`. Read-only: no `Set-ExecutionPolicy` anywhere but Option B's `-Scope Process`, no network, nothing started except the version-printing tools and nvidia-smi/vulkaninfo/wsl, Craft apps found by folder name only. Nothing in the kit names the subject, the surprise or the premiere; the README speaks of "family material" once, in the VeraCrypt section, which is no more than `CHARTER.md` already says in the same public folder. No family media is created or simulated; every fixture is invented and generated by `make_fixtures.py --check`. One dependency sits outside the package: `.gitignore` still has none of the Q-3 patterns (`pc_report*.json`, `*.local.*`, `logs/`), and the README now tells the maker to create `scripts/public_lint.deny.local.txt` (nudge 4, orchestrator).

**Maker usability (4).** The README is in plain language, every fence parses, each named section is present (whole folder, one-session policy with Options A and B, `Get-ExecutionPolicy -List`, `Unblock-File`, the Group Policy stop, the 3-minute run, read before pasting, the refusal section with the short-name explanation, the six paste-in commands, what comes next by title, the VeraCrypt admin-create / project-account-mount rule from W-25). "Not yet tested on a real Windows PC" is stated in bold where the maker will read it. Small things: the word "orchestrator" is used without a one-line gloss; the "If it fails" heading would be clearer as "If the script will not run at all"; the README does not say that the pasted report is about 100 lines and that this is expected. None of these blocks a learner.

**Fidelity to plan and DECISIONS.md (4).** The 4.4 fields, the 4.7 console contract, the 4.13 consumer contract, the 4.16 derived file and the W-22 pins (including FilmCraft fallback 0.8.0, retired 0.7.2, SoundCraft unpinned per D-12) are all as written. Thirteen deviations are listed and each is justified; the ones that change a shared contract need the orchestrator's nod rather than mine: D4 (`powershell.edition` values `WindowsPowerShell` / `PowerShell` instead of `Desktop` / `Core`, to stop the word `Desktop` colliding with default computer names; WP-02, WP-09 and WP-11b read this schema), D5 (exit 3 for the kit's own missing data files), D7 (non-NVIDIA cards capped at `gpu-low` until a test says otherwise; data, (J)), D9 (ImageMagick, Inkscape, Blender found by file and never started). Report section 6.2 raises two real 4.13 points for WP-03 (`vulkan.devices[]` is a list of strings so the `driver_version` exemption never applies; `vulkan.devices[]` should be a hardware-name field) (nudge 5).

**Maintainability (4).** Thresholds and pins are data with a `source` on every block and (J) on every guess; fixtures come from one generator with `--check`; the two scanners are structurally parallel (same function names and order in Python and PowerShell), which is what makes the 110-sample agreement test meaningful; `ps_lint.py` rules carry ids. The script is long for a PowerShell file but each step is one labelled block, and the non-obvious choices (the edition relabel, the registry constant written in pieces, the two-pass scan) carry a comment at the line. The pattern-file loaders accept several alternative key names (D13); that was prudent while WP-03's file did not exist and is now slack that could be tightened to the frozen names in a later round, not before P-LOCK.

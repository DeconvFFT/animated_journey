## 2. Tests of my own, designed to break it

**A. The static `lj.ps1` scan (`lj_problems`, `MUTATING`).** I appended nineteen one-line plants to a copy of `win/lj.ps1`. Caught: `Remove-Item`, `& git commit`, `[IO.File]::WriteAllText`. **Missed (16):** `rd`, `rmdir`, `mkdir`, `'x' > $file`, `$log >> $file`, `Invoke-Expression $cmd`, `iex`, `Start-Process git -ArgumentList 'commit'`, `Export-Csv`, `Tee-Object -FilePath`, `Compress-Archive`, `& git -C $repo commit` (an option between `git` and the verb), `git.exe --no-pager push`, `& 'git' commit`, `& 'Remove-Item' $x` and `$c = 'Remove-Item'; & $c $x` (the literal-stripping removes the command name). The test's actual text "no mutating command in the code" is stronger than what the scan can show. WP-01b's `tests/win_lj/` proves the behaviour on fake trees (nothing changes, nothing is written) and Fable approved that in round 2, so this is not a safety hole today, but the claim and the oracle should match (nudge 4).

**B. The disk rule from envelopes (`budget_problems`, `crossing_problems`).** A planted envelope with `planned_write_mb 150, avail_mb_min 260, floor_mb 0, hard_floor_mb 0` passes both functions: the checker trusts the envelope's own floor fields instead of the plan's 400 and 250. No real envelope does this (all 1,751 carry 400/250), so the live result stands, but a package can lower its own floor and the integration test would not notice (nudge 3). A string `planned_write_mb` crashes the test to FAIL (fail closed; acceptable). A `None` minimum is flagged. Good.

**C. The readiness parser (`readiness_problems`).** PASS on a row with `Yes`, `yes (CIM)` or lower-case `pass (container)` is caught; an escaped pipe inside a cell does not shift the columns in a way that hides anything. **An added row `M9` with "Needs Windows: yes" and `PASS (container)` is silently ignored** because the row regex accepts `M1` to `M8` and `C` only (nudge 5).

**D. `--only` destroys the mode's evidence file.** `run_checks.py` truncates `tests_<mode>.jsonl` and rewrites `summary_<mode>.json` on every start, `--only` included (reproduced into a scratch evidence folder: `--only index.thirteen` leaves a one-line `tests_quick.jsonl` and a summary of "1 PASS"). `make_evidence.sh` runs `--only index.thirteen,readiness` after `run_week2_checks.sh --quick` and before `--all`, so a complete `make_evidence.sh` run ends with a two-envelope quick file and a "2 PASS" quick summary, which the next runner pass would index as WP-11b's quick result. The delivered evidence is whole only because the implementor re-ran `--quick` by hand at 20:24 after the transcript (20:23) (nudge 2).

**E. Register against oracle.** The parity test for the card's Phone row computes its expected strings from `pipeline/phone/profile.json` (PH2 `-maxrate 3500k`, `max_chars_per_line 32`). `DECISIONS.md` W-63 says PH2 has a **4 Mb/s cap** and W-18 says **at most 36 characters**; `profile.json`'s own `status` field admits "32 is the build plan's figure (W-18 says 36)", and WP-08 round 1 (nudge 3) already said the register wins and the profile should carry 4. The card, which matches the register on both, is the file this test fails, and its printed FIX tells the orchestrator to paste `PHONE-ROW.md` over it. The staged `SKILL.md` step 16 meanwhile still reads "PH2 ... 4 Mb/s cap", so the package's own skill text contradicts the package's own test. See section 3.

## 3. Critical issue

**The oracle for `parity.card_phone_row_vs_phone_row_md` treats `profile.json` as the truth where `DECISIONS.md` speaks (W-63: PH2 4 Mb/s cap; W-18: 36 characters), and its FIX line instructs a paste that would write 3.5 Mb/s and 32 characters into the settings card the maker signs on Sun 1 Nov.** The plan did ask for "phone row = PHONE-ROW.md/profile.json", and the readiness map does say "decide 32 or 36 first", but the PH2 cap conflict is presented everywhere (test output, finding 2, M5) as the card being stale rather than the profile deviating from the register, and `DECISIONS.md` wins over the plan. Until the register is amended or the profile regenerated, the test must name `profile.json` as the file that disagrees with the register, and nothing in this package may instruct a change to the card against W-63 or W-18. Nudge 1 is the fix; it is small.

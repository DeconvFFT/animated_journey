## 3. Tests of my own, designed to break it

All against the local stand-in release server from `tests/sp1/make_fake_release.py`, with the fake 2000 MB `df`, in a scratch folder removed afterwards.

1. **A wrong hash in the guide.** One hex digit changed in the PhotoCraft row of a copy of `MAKER-CRAFT-ZIPS.md`: G4 FAILs three ways (table row, fence entry, stray 64-hex string). Good.
2. **A stage for an app that is not in this spike** (`--only photocraft v0.10.0`): refused, exit 2, names the three valid stages. Good.
3. **A corrupted kept tarball.** Ran the FilmCraft stage once (tarball kept in `_keep/`), flipped one byte of the kept file, ran again. The stage says `[1/6] a kept, verified tarball exists in _keep/` (it is not verified yet), verify correctly REJECTs it before extraction, exit 1, **but the corrupt file stays in `_keep/`**, so the third run fails the same way, and so would every later run and WP-10's T3 hand-off. Nothing re-fetches. **Critical issue 2.**
4. **A hash mismatch on 0.9.0 during `--all`** (the `--flip-byte filmcraft` tree): the 0.9.0 download is REJECTED, then the runner prints `FilmCraft 0.9.0 failed T1 or T2 (exit 1), so the fallback 0.8.0 is fetched`, downloads 0.8.0, and carries on to EffectCraft. The plan says a mismatch is **stop and report** and that 0.8.0 is fetched **only if 0.9.0 fails T1 or T2**. Both are broken by the one exit code. **Critical issue 1.**
5. **A stray stage envelope from the forced-404 acceptance line.** After test 4 of section 2 (the plan's own acceptance command), `stage_filmcraft-v0.9.0.json` says BLOCKED "download blocked or asset missing", and `verdict.py --print` then reports T1 FilmCraft and T2 as `NOT RUN: ... download blocked or asset missing: see blocked_proof.json`, which is false (downloads are reachable). `run_tests.sh` deletes that file by hand (line 142), which shows the author met it; the by-hand acceptance line and the verdict do not. I removed the stray file after the test. Nudge 3.
6. **The "where did it write" line against folders named like people.** Made-up profile with `AppData\Local\Microsoft\Outlook\someone.name@example.com` and `AppData\Local\Packages\Family Photos 2019`: both are printed in full after the `%USERPROFILE%` prefix. G6 only checks the prefix. The guide's "read the lines before you paste, delete a line that shows a name" is the only guard. Nudge 4.
7. **`--profile full` at the fake 900 MB**: exit 3 with "Neither profile fits", although lean fits and `--list` without `--profile` says so. Nudge 6.

## 4. Findings by criterion

**Correctness (3).** The main paths are right and well tested: the guard sits around every real write, the hash is checked before `tar -t` and `tar -x` (G7 proves the order from the script text and a flipped byte), the plan-versus-budget check before extraction, the keep rule, the reuse of a kept tarball, the cleanup trap that ignores a second TERM, the ledger, the 10 GB session-RSS watchdog, the ten planted defects that each fail exactly their own criterion. The two critical issues are both on the hash-rejection path, where the exit code 1 ("a test failed") is also used for "the file is not the file" (`run_sp1.sh` line 200), so `--all` (line 286) reads a stop-and-report as a FilmCraft failure, fetches the fallback and keeps going, and a bad kept tarball is never cleared (line 199 spares it). Smaller: `verdict.py` cannot tell a forced-404 stage envelope from a real block (test 5); the stage `timeout` of 60 minutes (line 151) can kill a real T2 after its 20-minute H.264 export and the N=300 import, and `t2_filmcraft.py` writes its envelope only at the very end, so a timeout would lose every measurement taken (nudge 5).

**Safety and privacy (4).** Redaction by design is present almost everywhere: `scrub()` on every string that reaches an envelope, URLs without query, no proxy address, repo-relative paths, the public lint clean over the owned paths, `env -i` with a throw-away HOME and `unshare -rn` for the untrusted binaries, downloads into a new empty folder, Python with `-I`. The Windows fences are read-only unless marked, parse on pwsh 7.5.4, pass `ps_lint.py`'s 5.1 rules, print no profile path on the happy path, and the guide never names the Launcher as something to install. Test content is geometry, digits and the string `TEST 0123` (4.10 kept). Nothing could tip off the mother and no family media is touched or simulated. The gap is test 6: the WP-01b input line prints AppData folder names verbatim, and such names can be an email address, an account or an album; the fix is one `-replace` (nudge 4). Step 2's `Move-Item` would also echo a full `C:\Users\<name>\Downloads\...` path in its error text if a move fails; a `try/catch` that prints only the file name closes it.

**Maker usability (4).** The guide is plain, ASCII, in order, says what each box does before it runs, marks every writing box, gives the folder rule the inventory script scans, tells the maker what to write down and in what order to paste, and points to the exact playbook sections (all of which exist) instead of copying them, with the folder correction for the playbooks' `C:\LifeJourney` and `Program Files` paths. The generated table means no hash is typed by hand, and `guide.in_sync_with_assets` keeps it that way. Good touches: "an empty answer is an answer", the fallback zip "skip it for now", the three graphics fallbacks in the order R7 gives them. Nudge 6 is the only wording issue I found on the container side.

**Fidelity to plan (4).** Every deliverable of the WP-07 section exists in the form asked: `release_assets.json` from all six lists with the six R8 values compared (all match) and the three integrity-only pins said so; SoundCraft "not pinned, not fetched"; the guide with the two read-only where-did-it-write lines; `run_sp1.sh` with one `lj_with_disk` per app, profiles from live Avail, the keep rule, the 0.8.0 condition; `blocked_proof.json` and `FALLBACK.md` written in advance; `VERDICT-SP1A.md` generated with T3, T5 and T6 worded as the plan says. The download ledger holds 0 fetches, as it should. Deviations are listed and sensible (sums fetched Monday; preflight HEAD before the guard; the blocked proof under `build/evidence/wp07/`). The one departure from the plan's rules is critical issue 1 (mismatch must stop, not fall back). T1, T2 and T4 not run is the R-11 case the plan foresaw, and the report asks for Q-1 by name.

**Maintainability (4).** Small, config-driven (`config.json` holds every budget, profile and pass mark; `r8_hashes.json` holds the independent values with their source lines), the guide is generated, the verdict is generated, drivers share `sp1_lib.py`, the stand-ins exercise the unmodified runner through environment overrides only, and `run_tests.sh` is one line per test with an envelope each. `sp1_lib.py` at 590 lines and `t2_filmcraft.py` at 463 are at the top of comfortable but readable and commented where it matters (the session-RSS watchdog, the TERM handling, the ticks). The hash-rejection fix should come with its own stand-in test so the path stays covered.

## 5. Nudges (at most six; the first two are the critical issues)

1. **Hash mismatch must stop and report, never fall back.** `spikes/sp1_craft_cli/run_sp1.sh`: in `stage_inner` (lines 196 to 201) return a distinct code for a rejected tarball (for example 4, documented in the header next to 4.3's codes, or write `$EVID/.hash_rejected_<id>` before `return 1`); in the `all` branch (lines 285 to 291) treat that as "STOP AND REPORT: the 0.9.0 tarball did not match; 0.8.0 is not fetched and EffectCraft is not started", exit 1; make `finalize_stage.py` write `status FAIL`, reason "hash mismatch (stop and report)". Add `fake.hash_mismatch_stops_all` to `tests/sp1/run_tests.sh` with the `flip` tree: expect no 0.8.0 line in the ledger and no EffectCraft stage.
2. **A kept tarball that fails verify is removed, and the run can recover.** `run_sp1.sh` line 199: when `reused=1`, `rm -f -- "$kept"`, print "the kept tarball was corrupt and has been removed; the next run downloads it again (ledger exception)", and either fall through to the download in the same stage or return 3 with that message; `asset_tool.py ledger --add ... --exception "kept tarball rejected"` on the re-fetch. Reword line 187 to "a kept tarball exists in _keep/ (re-verified in the next step)". Add `fake.kept_tarball_corrupt_recovers` to `run_tests.sh` (flip a byte in `_keep/`, run twice, expect exit 0 on the second run and 2 ledger lines, the second with an exception).
3. **Forced-404 stage envelopes must not reach the verdict.** `spikes/sp1_craft_cli/drivers/finalize_stage.py`: when `FORCE_BAD_ASSET=1`, put `"forced_bad_asset": true` into `detail` (and preferably name the file `stage_<id>_forced.json`); `drivers/verdict.py` `stage_reason()`: skip envelopes with that flag, as `build()` already does for `blocked_proof.json`. Then drop the hand `rm -f` at `tests/sp1/run_tests.sh` line 142 and assert instead that `verdict.py --print` after the forced line still says "no stage has produced a result yet" for FilmCraft.
4. **Redact names inside the where-did-it-write output by design.** `spikes/sp1_craft_cli/build_guide.py`, the `where_appdata` fence: after computing `$rel`, replace any path segment containing `@` or a space-separated name-like segment the maker could not vet with `<redacted>` (at least `$rel = $rel -replace '[^\\]*@[^\\]*', '<redacted>'`), and consider `-Depth 2`; in the Step 2 fence wrap `Move-Item` in `try { ... } catch { 'could not move: ' + $n }` so no `C:\Users\<name>` path is ever echoed. Extend `check_guide.py` G6 with a made-up `x@y` folder and assert `@` never appears in the output. Regenerate the guide and re-run `check_guide.py`.
5. **A 60-minute stage must not lose T2's measurements.** `spikes/sp1_craft_cli/drivers/t2_filmcraft.py`: write the envelope after every phase (`phase_scaling`, `phase_export`, `phase_kenburns_dissolve`) with status `UNVERIFIED` and note "stage still running" until the final write, so a `timeout` or a DISK-FLOOR leaves the criteria measured so far; or set `SP1_STAGE_TIMEOUT_S` per stage in `config.json` (FilmCraft 5400) with the plan's 60-minute rule noted as the reason to split scaling and export into two stages that reuse the kept tarball. Say in `README.md` which it is.
6. **`--profile full` when only lean fits.** `run_sp1.sh` `do_list()` lines 100 to 106: when `$want` is `full` and lean would fit, print "the full profile is refused at this Avail; lean would fit: rerun with --profile lean (or auto)" and keep exit 3, instead of "Neither profile fits".

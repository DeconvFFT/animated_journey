### 0.3 The vendor's own status statements (from the READMEs, all self-assessed)

- **PhotoCraft** (README badge "early alpha"): "not yet a Photoshop replacement for daily professional work." PSD claims: re-saving "renders the same for 307 of the 309 files in the psd-tools test set and 169 of 170 in our mixed ag-psd/psd-tools set"; a re-saved PSD is **not byte-identical** (image resources, layer records and composite are rewritten); unmodelled blocks are carried over. The website says "134 of 135 real-world test files round-trip byte for byte" — a different corpus and a different claim. Also reads/writes **OpenRaster (ORA)**, layered TIFF, reads Paint.NET PDN3, SVG, Affinity documents; has its own `.pcraft` format (documented in the mdBook: `book/src/formats/pcraft.md`).
- **VectorCraft** ("Where we are (2026-10-10): alpha"): ~88% of Illustrator 2026 menu items exist, "~65% ready for real work" by its own estimate; "scripting" is listed as **missing** (the agent route is the command API/MCP, not a scripting language); documented native JSON format `.vectorcraft`; SVG, PDF, `.ai`-as-PDF import/export; PSD out; "property-tested file round trips"; `docs/development.md#robustness-vectorcraft-never-crashes`.
- **LightCraft** ("alpha"): "~61% as a day-to-day Lightroom replacement"; crash-safe op-log library; XMP sidecars and reads `crs:` develop settings; `.lcpreset` and XMP presets; export with naming templates and batch; CLI `lightcraft-cli run …` and `render in.dng -o out.jpg --set … --preset …`; "no account, no cloud, no telemetry."
- **FilmCraft** ("alpha", re-measured 2026-10-10 against Premiere Pro 26.5.2): "Ready for real work: ~56%"; **"Windows and Linux get far less testing than macOS"**; H.264 is the only software delivery codec (HEVC export is hardware-only), ProRes 422 HQ and DNxHR export exist; "camera and phone files in the wild are less tested"; Lumetri, keys and export render on the CPU; no plugins. Interchange: FCP7 XML, **FCPXML 1.9–1.11, OpenTimelineIO (round-tripping FilmCraft detail through `metadata.filmcraft`), CMX 3600 EDL, AAF, OMF**. Project file `.fcproj` is **UTF-8 JSON with `schema_version` 13**, media referenced by path, atomic saves, rolling auto-save versions and a crash-recovery journal (`docs/project-files.md`). The README documents Windows GPU-driver crashes on some AMD systems and a `WGPU_BACKEND` override.
- **EffectCraft** ("alpha"): **"its first commit was on 1 October 2026"** (seventeen days before this review); "about 91% of After Effects' features exist … about 45% of the way to replacing After Effects"; **"Linux and Windows users have hit basic interaction bugs"**; cannot open `.aep`; project file `.ecproj` is "readable versioned JSON"; JavaScript expressions "with the After Effects object model (`wiggle`, `loopOut`…)"; **Lottie import and export** (export lists what Lottie cannot express); export H.264, ProRes 4444 with alpha, HEVC, AV1, WebM with alpha, PNG/JPEG/TIFF/EXR sequences, GIF, WAV/AIFF; render queue runs from the command line; optional MobileSAM roto and MediaPipe face tracking as separate downloads; "no telemetry, and no network access unless you ask for it." The website says "259 effects", the README says "306 effects": the number changed in the time between page updates.
- **SoundCraft** (README badge **"pre-alpha"**): "roughly 40% of the way to replacing it for real work"; choosing an audio interface and buffer size, MIDI recording and AAF/OMF interchange are still missing; autosave with recovery; CLAP plugin hosting; a picture track for video sync; "the code never panics on bad input."

### 0.4 Every app is "built for agents": CLI, JSON control channel, MCP server

All six READMEs describe the same architecture: every menu item is a command with an id and JSON parameters, dispatched identically from the UI, a `<app>-cli` binary, a loopback JSON-lines control channel (`<app> --control <port>`) and an **MCP server** (`<app>-cli mcp`, headless, or bridged to the running app with screenshots and widget-level clicks). Examples seen: `photocraft-cli run wave.psd --cmd … --out …`, `photocraft-cli batch --actions grade.json --in ./raw --out ./graded`; `vectorcraft-cli run --in file.vectorcraft --export out.pdf`; `lightcraft-cli render in.dng -o out.jpg --set light.exposure=0.7`; FilmCraft `timeline.place` and `effects.setParam` over JSON; `effectcraft-cli render --comp Main --out main.mp4`, `effectcraft-cli exec file.exportLottie …`; `soundcraft-cli run --demo --cmd 'mix.volume=…' --bounce mix.wav`.

Crucially, **EffectCraft's `docs/agents.md` states that release packages ship the CLI**: Windows MSI installs `C:\Program Files\EffectCraft\effectcraft-cli.exe` (not on PATH); Linux deb/rpm install `/usr/bin/effectcraft-cli`; and headless MCP **"renders on the CPU unless you add `--gpu`"**. The FilmCraft README says its Linux tarball installer "places FilmCraft, its command-line tool and desktop integration". The website's download pages list the CLI only as a macOS zip, which is misleading.

Why this matters: the charter frames the Craft apps as refinement layers for human hands. The code says they are also **agent-drivable, headless, CPU-rendering engines with Linux builds**. That is a candidate rendering path inside the cloud container, and a GUI-control path on Windows that needs neither the desktop app nor computer use (see Part 1). Both must be verified against the code and a real install before anything depends on them, because the same READMEs say Windows and Linux are the least-tested platforms.

### 0.5 Web builds

Each release ships `<app>-web-<ver>.zip`, "a static site; host it on any static server". FilmCraft's `docs/web.md`: wasm32 + wasm-bindgen glue, eframe web runner on **WebGPU with WebGL2 fallback**, URL flags `?cpu` (CPU compositor), `?webgl`, `?empty`, `?norecover`; the server must send COOP/COEP headers and serve `.wasm` as `application/wasm`; media stay local in OPFS. PhotoCraft has a Docker hosting note (`packaging/web/README.md`). So an agent could plausibly load an app in headless Chromium with Playwright to *learn the UI*; whether that is worth the effort versus the CLI/MCP route is a research question, not a given.

### 0.6 Licences and provenance

All six repos: MIT or Apache-2.0 at your option (README). Each repo has an `AGENTS.md` with clean-room rules, which, together with the pace (thirteen apps; a compositor with "306 effects" seventeen days after its first commit; several hundred branches on the larger repos; `docs/agents.md` describing "how agents develop it"), indicates a codebase produced largely by AI coding agents. That is not a disqualifier, but it changes how to read claims: **"exists" means a command and a code path exist; it does not mean the behaviour was exercised by a human on Windows with real files.** Researchers should look for tests, oracles and corpora per feature we need, not per app.

## Part 1 — How these facts change the plan

1.1 **Reframe the Craft apps as "engines with a GUI", used in three tiers.** Keep the charter's rule that no critical step may depend on one alpha app, but stop treating the apps as GUI-only. Proposed tiers, to be confirmed by the two craft tracks:
- *Tier A — use now, low risk, GUI touch-ups with a proven fallback beside it:* PhotoCraft for layered touch-ups of agent-made ORA/PSD (fallback GIMP or Krita); VectorCraft for SVG touch-ups (fallback Inkscape); LightCraft for batch tone-matching of scans if its JPEG/TIFF path is sound (fallback darktable or RawTherapee, or ImageMagick batch).
- *Tier B — test in week 2 before relying on it:* FilmCraft fed by agent-written OTIO/FCPXML (fallback DaVinci Resolve free or Kdenlive, which also read those formats); EffectCraft fed by agent-written Lottie or `.ecproj` (fallback: the code-to-video route itself, since EffectCraft would be the refinement step for it).
- *Tier C — not on the critical path:* SoundCraft (pre-alpha). Audio mixing stays in Audacity plus ffmpeg (`loudnorm`, `sidechaincompress`) until SoundCraft reaches alpha; it may be used for the maker's learning only.

1.2 **Open a Phase-1 spike, not research: "Craft headless in the container".** Install one signed Linux release (deb or tarball, not a source build) of EffectCraft and FilmCraft in a fresh cloud container, run `effectcraft-cli render` on a tiny `.ecproj` and `filmcraft-cli` on a two-still OTIO, on CPU, and record wall time and RSS. This decides whether the apps are a *rendering* option for agents or only a *refinement* option for the maker. It belongs to the first week of the Design phase and is explicitly out of scope for the researchers (no running code); the `agent-pipeline` track should scope it.

1.3 **The GUI-control problem on Windows has a cheaper answer than computer use.** The computed brief notes that CLI computer use is macOS-only and GUI control on Windows needs the desktop app. The apps' own `--control <port>` channel plus `<app>-cli mcp --bridge/--connect` give widget-level control and screenshots of the *running* app from any MCP client, including Claude Code CLI in a Windows terminal. If Claude Code CLI on Windows is light enough for the maker's PC (verify), the desktop app is not needed. The `agent-pipeline` track must verify (a) the loopback-only authentication model of these channels (PhotoCraft documents an "automation security model"), and (b) that the Windows MSI of each app actually contains the CLI.

1.4 **Pin versions; turn off auto-update during production.** `.fcproj` is already at schema version 13; EffectCraft shipped three minor versions in its first seventeen days. Rule for the build phase: the maker installs the *portable* Windows builds of the chosen tags into a project folder, the repo records the tags, and the Launcher's updater is not used until a deliberate upgrade gate. Agent-authored project files carry the tag they were written for.

1.5 **Privacy stance for the Craft apps: "offline by default, verify in code".** LightCraft and EffectCraft state no telemetry and no network unless asked. The craft tracks should grep each repo for HTTP clients and update checks and list every code path that touches the network (optional model downloads, Launcher polling, MCP bridges). Family photos never enter the hosted ArtCraft studio.

1.6 **The surprise changes the gathering plan more than the pipeline.** Review 00 argued that Gather must start in week 1. The maker now says material comes "once the pipeline is locked". With a surprise, the slow parts (borrowing albums without being noticed, labs digitising tape, relatives recording voice memos, the one family gathering at the holidays) are slower still. `surprise-ops` must deliver a dated digitization and interview plan so the maker can start *covert collection* now while the pipeline is still being locked; the two are not in conflict.

1.7 **The maker's hardware inventory is still missing** (review 00, 1.3 item 2). Windows is now known; CPU, RAM, GPU/VRAM, disk, scanner and upload speed are not. Three tracks (craft-visual, craft-motion, agent-pipeline) must write recommendations as decision tables keyed on these, as before.

1.8 **A Craft-specific rubric line.** Under Accuracy, for anything about the Craft apps: *"Claim is backed by a cited source file or test in the repo at a named tag, or by a dated first-hand report; marketing pages and README percentages are leads, not evidence."*

### 2.1 `craft-visual` — PhotoCraft, VectorCraft, LightCraft as refinement layers (and possibly engines)

## Part 4 — Advisor insight

The surprise is usually treated as a constraint. It is also the piece's best structural device. Everything in the film will be *other people's* memories of her: her sister's version of the house, her friend's version of the first job, her child's version of the kitchen. If the piece admits this openly, chapter by chapter, with each chapter visibly "told by" one person (their voice, their handwriting on the title, their one object), the inevitable gaps and contradictions become the point rather than a flaw: this is what she looks like from the outside, to the people who love her. Then the "gift after the gift" writes itself: the last chapter is empty, titled in her name, waiting for her version. No tool decision depends on this, but every tool decision becomes easier once the structure is chosen, because each chapter needs only one voice, one object and one place.

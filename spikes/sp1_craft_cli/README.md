# SP1a: the Craft command-line programs in the container (WP-07)

*Spike SP1, part a. Built Mon 19 Oct 2026 (build plan section 5, WP-07). `DECISIONS.md` wins over this file.*

**The question.** Are `filmcraft-cli` and `effectcraft-cli` usable as a CPU-only render engine for agents in the cloud container (ROADMAP 5.2: "Craft CLIs: only if SP1 T2/T4 pass"), or are FilmCraft and EffectCraft only refinement tools on the maker's PC? **The other job** is the maker's Craft-zip guide for Sat 24 Oct.

**What this covers.** FilmCraft 0.9.0 (T1, T2) and EffectCraft 0.11.1 (T1, T4). PhotoCraft, VectorCraft and LightCraft move wholly to WP-10 (so each tarball is downloaded once in the fortnight). SoundCraft (T5) is not run: it is unpinned and learning-only (D-12). The web builds (T6) are not pins. T3 (interchange) is WP-10's, from the FilmCraft tarball this package keeps.

## How to run it

```sh
bash spikes/sp1_craft_cli/run_sp1.sh --list           # the plan, df, the profile it would choose; exit 3 if Avail minus planned is under 400 MB
bash spikes/sp1_craft_cli/run_sp1.sh --sums-only      # six small text files and 12 HEAD requests; writes release_assets.json
bash spikes/sp1_craft_cli/run_sp1.sh --only effectcraft v0.11.1 --t1-only    # one real download, the smoke test, everything deleted
nohup bash spikes/sp1_craft_cli/run_sp1.sh --all > /dev/null 2>&1 &         # the full staged run: hours; background; disk and bench locks
python3 -I spikes/sp1_craft_cli/drivers/verdict.py    # (re)write VERDICT-SP1A.md from the evidence
python3 -I spikes/sp1_craft_cli/check_guide.py        # the guide against the table and its own safety rules
bash tests/sp1/run_tests.sh --quick                   # at most a minute, no downloads;  --all adds the network lines and the stand-in mechanism tests
bash spikes/sp1_craft_cli/run_sp1.sh --list --profile full   # exit 3 with "lean would fit: rerun with --profile lean (or auto)" when only lean fits
```

## How a stage keeps the disk and the machine safe

- **Disk is code.** Each stage is one `lj_with_disk PLANNED LABEL --` call (`scripts/lj_guard.sh`): it takes `disk.lock`, refuses unless Avail minus planned stays at or above 400 MB, and stops the whole stage if Avail falls under 250 MB. Profile `full` (FilmCraft 600 MB, EffectCraft 400) is chosen only if it fits; else `lean` (350, 300): only the CLI members of the tarball are extracted and the ProRes test is one second. Neither fits: exit 3 with the shortfall and Q-1 (the pip cache). The lean profile changes sizes and durations, never a pass mark.
- **A new empty folder, then a hash, then tar.** The tarball goes into `vendor/craft/<app>-<tag>/` (git-ignored), its SHA-256 is checked against `release_assets.json` and the independent value **before** it is listed or extracted. A mismatch stops, deletes the tarball and extracts nothing, and it is **stop and report**, never a failed test: the stage returns the internal code 4 (run_sp1.sh itself exits 1), the stage envelope says `FAIL`, "hash mismatch (stop and report)", and `--all` then fetches no 0.8.0 fallback and starts no EffectCraft stage (the fallback is fetched only when 0.9.0 *passed the hash* and failed T1 or T2).
- **Untrusted binaries.** The Craft program is run by absolute path under `env -i` with a throw-away `HOME`/`TMPDIR`/`XDG_*`, `timeout`, `unshare -rn` (no network, when it works) and a watchdog that sums the resident memory of its whole session every quarter second and kills it at 10 GB (`ulimit -v` is not used: wgpu maps large address ranges). The program is only ever given synthetic stills. Nothing is run from inside a downloaded tree except the CLI under test, and no build tool, package manager or interpreter is.
- **The 60-minute cap and partial results.** A locked stage is at most 60 minutes (build plan 4.9, `SP1_STAGE_TIMEOUT_S` to change it for a one-off). The plan's rule is kept as it is, not split or extended: FilmCraft's T2 would otherwise lose every measurement if the cap, a DISK-FLOOR stop or a crash ended it during the 20-minute H.264 export. So `t2_filmcraft.py` writes its envelope **after every phase** (scaling, export, Ken Burns and dissolve) as `UNVERIFIED`, `detail.partial`, "stage still running", and replaces it when the run ends; a TERM also writes a "stopped" envelope, and a KILL leaves the last phase's. `verdict.py` shows such a result as `INCOMPLETE` with the criteria measured so far. A partial result is never a PASS.
- **Timing.** The test drivers run under `lj_bench` (one timed run at a time; the load at the start is recorded; a run with another job's load visible is marked contaminated).
- **Keep rule.** The verified FilmCraft 0.9.0 tarball (70 MB) is moved to `vendor/craft/_keep/` for WP-10's T3 if Avail after cleanup is at least 700 MB, else deleted (WP-10 re-fetches once, a recorded ledger exception). `_keep/` is a hand-off folder: WP-07 creates it, WP-10 consumes and deletes it. A kept tarball is **re-verified every time it is reused**; one that fails the check is deleted at once (so no later run can fail on it) and fetched again in the same stage, recorded as a ledger exception ("kept tarball rejected").
- **Ledger.** Every real download adds a line to `build/evidence/wp07/download_ledger.jsonl`; `--ledger-check` fails if a tarball was fetched twice without an exception or the total passes 2 GB.
- **Blocked.** A HEAD that does not answer 200 (or a failing download) writes `build/evidence/wp07/blocked_proof.json` (URL without query, status, curl exit code, curl's stderr word for word, the HTTP status lines, the time) and exits 3. See `FALLBACK.md`.

## What the tests cover, and what they cannot

`bash tests/sp1/run_tests.sh --all` runs the real network lines **and** the same runner against a local fake release server with stand-in CLIs (`tests/sp1/fake_craft/`) and a fake `df`. The stand-ins implement just the command surface the drivers use, with planted defects: each defect must make exactly its own criterion fail, so a driver that cannot fail would be caught. **The stand-ins are not FilmCraft or EffectCraft and say nothing about them.** A real pass needs the real tarball and a disk the guard accepts.

**UNVERIFIED, whatever the result:** anything about Windows (a Linux CLI run proves nothing about the apps' windows, drivers or the maker's PC); the exact command parameters of the real CLIs (the drivers read them from `describe` and record every call, and a surprise ends as `UNVERIFIED (the driver could not drive the CLI)`, never as a verdict on the app); the FilmCraft keyframe convention for clips that do not start at 0 (the driver assumes clip-relative times, as `research/cinematic-quality-fixtures/filmcraft_push.py` does for a clip at 0); the Parallax comp uses solids and shapes, not imported footage.

```bash

```

## 5. Deviations from the plan, with the reason

**D-1. The disk stage did not run inside `lj_with_disk`.** The plan says the test renders run as one `lj_with_disk 150` stage. The guard refuses unless Avail minus planned is at least 400 MB, and the volume sat between 147 and about 450 MB while I worked (it read 394 MB when I tried the stage as specified: `REFUSED: Avail 394 MB minus planned 150 MB leaves 244 MB`, in `guard_refusal_as_specified.txt`). At that level even a 0 MB stage is refused. I did four things, in order. (1) I measured the real peak of the generated files: **20.2 MB**, not 150 (fixtures are flat patches; clips and frames are deleted straight after use). (2) I added a lean profile: planned 150 when Avail is at least 550, else 30 (20.2 plus 25%, rounded up, per 4.9). (3) I let `run_tests.sh --all --wait` poll for about 11 minutes for Avail of at least 430 MB; it never came (range 280 to 416 MB). (4) I ran with `--unguarded`: the guard is still tried first, its refusal is printed and ledgered (`"status":"refused"` in `guard_stage.json`), and the stage is recorded as **SKIPPED** with the exact message, run under the 4.9 rule that writes under 100 MB take no lock. The run never went below 327 MB Avail. **To get the guarded evidence:** re-run `bash tests/validators/make_evidence.sh` when Avail is at least 580 MB (planned 150) or 430 MB (planned 30), or when the orchestrator answers Q-1 (clearing the 418 MB pip cache would do it). I did not delete anything that is not mine.

**D-2. BT.601-under-BT.709-tags exits 0 in `spec_check.py`, on purpose.** The task text lists it among the planted defects that "each exit 1", but the plan's oracle says it is the defect `spec_check.py` must **not** catch (tags pass, colour-patch fails), which is why both tools exist. I followed the oracle: ten defects exit 1 naming their check; this one exits 0 and is proven bad by luma 81 against 63 and by `colour_patch.py` (23/255).

**D-3. `expect.profile` is null in `chains.json`; the profile is in `expect_extra`.** 4.5 lists `profile` in `expect`, but `render.mjs` compares every non-null `expect` key against a fixed ffprobe set that has no `profile`, so a filled value would give a false mismatch after every render of `--chain h264_venue`. `colour_patch.py` and a parity test read `expect_extra`; `spec_check.py` profiles assert the profile independently. See F-3 for the one-line fix that lets `expect.profile` be filled later.

**D-4. Additive keys.** `chains.json`: `alpha`, `expect_extra`, `approved`, `measured`, `used_for`. `settings.json`: a fifth profile `overlay_prores4444_alpha`, and a `profile_fields` description. `colour_patch` derived record: `tolerance` and an optional `controls` array. All are additive; the 4.5 / 4.16 readers are unaffected.

**D-5. MO8 limits and stand-in masters.** The plan says "about 96 frames" in one place and "refuses a clip over 120" in another. The gate accepts up to 96 by default, up to 120 with `--max-frames`, and refuses everything above 120 always; it also refuses fewer than 12. Because of the disk budget the 96-frame clips are H.264 CRF 14 stand-ins for a master (the gate flags a lossy input as approximate); the PNG-folder test uses 12 grey PNG frames from the middle of the push. A first try with a smoother texture halved the file size but pushed the Pillow reading to 0.04 px, so the original grey chart (reused from `ab_push_card.py`) stays.

**D-6. Patch reading.** Each patch is read as the mean of a central 200 x 200 block (rounded), not a single pixel; the maximum single-pixel error is recorded as well. The oracle numbers match Q-F1 exactly either way.

**D-7. The container's raw colour-patch record is filed.** The plan's acceptance line writes `--json build/evidence/wp05/colour_patch_ffmpeg-6.1.1.json`, and the raw-never-filed rule (4.4) is about the maker's PC. This record is the container's public Ubuntu build (flags with `/usr` paths only); `public_lint.py` is clean on it. The tool's header, the README and the console all say that a PC raw record is pasted in chat only; the derived file is the one to file from the PC.

**D-8. `-B` on the wrapped audit.** `mo8_gate.py` runs the audit as `python3 -I -B` so no `.pyc` files appear in `research/` (a first run left two; I removed them). `gen_fixtures.py` sets `sys.dont_write_bytecode` for the same reason.

## 6. Findings

* **F-12 (new measurement).** The ProRes 422 HQ master chain measures **2/255** with the W-16 decode path, which leaves one level of margin to the limit of 3. Decoded with `flags=accurate_rnd+full_chroma_int` it measures **0**, so the file itself is correct BT.709 and the 2 comes from swscale's default 10-bit 4:2:2 to RGB24 decode (an exploratory read of the raw 10-bit values gave Y 250 / 504 / 685, exactly the BT.709 figures). Every chain's JSON carries both numbers (`worst_error`, `worst_error_accurate`). H.264 venue, backup and online: 1/255 each. ProRes 4444 and FFV1: 0. All six are `approved: true` on 6.1.1.
* **F-1. Oracle.** All six Q-F1 figures reproduce exactly on 6.1.1 (1, 1, 5, 23, 25, 0). No finding.
* **F-2. MO8 numbers differ from round 2 in size, not in verdict.** Pillow 0.0046 / 0.0095 px against about 0.003 reported; zoompan 0.82 / 0.30 px against about 0.6 reported. The content is different (a synthetic worst-case chart, H.264 CRF 14, against scanned prints); the 0.05 and 0.04 gates separate them by a factor of 100.
* **F-3. Integration with WP-04 (for WP-11b).** (a) `render.mjs` builds its post-render `got` object from `probe.codec_name, pix_fmt, width, height, color_*, r_frame_rate, nb_frames` and never copies `profile`; adding `profile: probe.profile` to `got` would let `expect.profile` be filled in `chains.json`. (b) `render.mjs`'s built-in `h264` chain has no `-profile:v high -level 4.1`; in an exploratory encode x264 chose level 4.0 for 1080p24 at CRF 18, so a file made with the built-in chain fails `spec_check.py`'s `venue_h264` profile (`video.level`; this is exactly the planted `d_level40` defect). Use `--chain h264_venue` for venue files. (c) The built-in chain will not equal `h264_venue` (the venue chain adds profile, level, maxrate, bufsize, faststart and `-map_metadata -1`), so a parity test should compare `vf` and the four colour tags only.
* **F-4. ffprobe omits `color_range` when it is unknown** (ProRes on 6.1.1); `spec_check.py` treats a missing key as `unknown`. ProRes 4444 is reported as `yuva444p12le` for a `yuva444p10le` encode; the profile accepts both.
* **F-5. Collateral failures are inherent**, not noise: 25 fps also breaks frame count; yuvj420p also breaks the range tag; 16-bit PCM also breaks the codec check; no moov also breaks atoms and faststart.
